I've been hacking on Antonio Cuni's SPy ("Static Python") project for a few months now; mostly on documentation and the CLI, but also a couple of features and some dev QoL enhancements. I thought I would write down what I've learned about SPy's internals and mechanisms, both for myself and for anyone else who wants to jump into the codebase

Consider this a snapshot of SPy at this moment in time - if you're reading this in the near or far future, know that SPy is changing fast. I've tried to note areas where it seems like things are most fluid, but that's just a best guess.

What is Spy?

Antonio wrote a whole blog post of what SPy is and why it exists, that's well worth reading.

SPy is an interpreter and a compiler for a statically typed variant of Python, with focus on performance.

...

SPy is a thought experiment to determine how much dynamicity we can remove from Python while still feeling Pythonic.

In essence, SPy is a very Python-like language, that's aimed to be relatively easy for Python developers to write, which allows for high-performance compilation to c (or WASM or other backends). Unless you're writing advanced library code, it looks very much like CPython:
{{< highlight python3 >}} # hello.spy def add(x: i32, y: i32) -> i32: return x + y def main() -> None: print("Hello from SPy") print(add(10, 20)) {{< /highlight >}}
If you want to see what SPy looks like, check out the examples on GitHub.

App Level vs. Interp Level

With SPy a deliberately python-like language, it's important to distinguish between objects, classes, etc that are inside the SPy interpreter and those that are part of the Python source that implements the interpreter. The former are app-level objects and the latter, low-level, implementation details are interp-level objects.

By way of comparison, in CPython, the app-level code would be Python, and the interp-level code would be C. These labels aren't really needed in something like CPython where the code looks very different, making it obvious whether you're lookng at Python code or interpreter implementation details. But in SPy, where the user-code and the interpreter-implementation-code are so similar, it's useful to have labels for each.

There is a naming system for variables which helps distinguish the two. From a comment in object.py:

In interp-level code, variables and fields which contains references to app-level objects are always prefixed with w_, which stans for "wrapped": e.g., the app-level SPy object `100` is represented by the interp-level instance `W_I32(100)`, which is a wrapper around the interp-level object `100`.

The (necessary) distinction between the two means that a fair amount of wrapping and unwrapping of variable types is necessary within the interpreter. See, for instance, vm.wrap() and the various flavors of vm.unwrap(), which convert, say, a string like hello inside the interpeter into a SPy string, which to the interpreter is a W_Str('hello').

MetaArg, OpImpl, OpSpec, and Operators

As a worked example, let's take a sample piece of SPy code and see how it is executed inside the interpreter, from the point that the program has already been parsed, imports mported, symbols identified, and we're ready to actually execute code: {{< highlight python3 >}} def main() -> None: a: int = 1 b: int = 2 c = a + b # <<< Our focus {{< /highlight >}}

Following the assignments on lines 2 and 3, both a and b are W_Int32 objects with value=1 and 2 respectively. The frame representing main() tracks that those local variables a and b not only point to those values, but that the symbols are blue and that their type is known to be i32.

{{< highlight python3 "linenos=false">}} { 'a': LocalVar(varname='a', color='blue', w_T=, w_val=W_I32(1)), 'b': LocalVar(varname='b', color='blue', w_T=, w_val=W_I32(2)) } {{< /highlight >}}

After parsing into an AST, line 4 of our code above has become:

{{< highlight python3>}} VarDef( kind=None, name=StrLiteral(value='c'), type=Name(id='int'), value=BinOp( op='+', left=Name(id='a'), right=Name(id='b'), ), ), {{< /highlight >}}

The BinOp expression gets evaluated by AstFrame.eval_expr_BinOp():

{{< highlight python3 >}} # spy/vm/astframe.py::AstFrame::eval_expr_BinOp() def eval_expr_BinOp(self, binop: ast.BinOp) -> W_MetaArg: w_OP = OP_from_token(binop.op) # e.g., w_ADD, w_MUL, etc. wam_l = self.eval_expr(binop.left) wam_r = self.eval_expr(binop.right) w_opimpl = self.vm.call_OP(binop.loc, w_OP, [wam_l, wam_r]) return self.eval_opimpl(binop, w_opimpl, [wam_l, wam_r]) {{< /highlight >}}

Let's examine the lines of this function one by one.

Line 2: w_OP = OP_from_token(binop.op)

OP_from_token looks up the symbol it was given in a table in the interpreter to get back a function name, in this case OP.w_ADD.

{{< highlight python3 >}} # spy/vm/modules/operator/binop.py @OP.builtin_func(color="blue") def w_ADD(vm: "SPyVM", wam_l: W_MetaArg, wam_r: W_MetaArg) -> W_OpImpl: from spy.vm.typechecker import typecheck_opspec w_ltype = wam_l.w_static_T if w_opspec := MM.get_binary_opspec("+", wam_l, wam_r): pass elif w_add := w_ltype.lookup_func(vm, "__add__"): w_opspec = vm.fast_metacall(w_add, [wam_l, wam_r]) else: w_opspec = W_OpSpec.NULL return typecheck_opspec( vm, w_opspec, [wam_l, wam_r], dispatch="multi", errmsg="cannot do `{0}` + `{1}`" ) {{< /highlight >}}

The OP.w_ADD function does two lookups - first, to see if the the types of its left and right operands are in a pre-computed table for operations, or, failing that, if the left operand implements an __add__ method. In this case, the lookup is successful, since an appropriate operation was declared by the line MM.register("+", "i32", "i32", OP.w_i32_add).

OP.w_i32_add is generated dynamically when opimpl_int.py is imported by the operator module. It substitutes in i32 where necessary into the 'template': {{< highlight python3 >}} # spy/vm/modules/operator/opimpl_int.py @OP.builtin_func(f"{T}_add") def w_add(vm: "SPyVM", w_a: WT, w_b: WT) -> WT: return _binop(vm, w_a, w_b, lambda a, b: a + b) {{< /highlight >}}

... where _binop() is: {{< highlight python3 >}} # spy/vm/modules/operator/opimpl_int.py def _binop(vm: "SPyVM", w_a: WT, w_b: WT, fn: Any) -> Any: a = w_a.value b = w_b.value res = fn(a, b) return vm.wrap(res) {{< /highlight >}}

So, we finally have our operation which claims claims to know how to add two i32 ints together - it takes their values, adds them together in python (via the lambda), wraps them up in a new integer, and returns that. It's important here to note that what we've determined is called in SPy terminology an OpSpec (class W_OpSpec), which contains the types that the operation is receiving and the type that it's emitting.
